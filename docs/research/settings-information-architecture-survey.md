# Settings information architecture survey

Research date: September 2026. Compiled to inform a redesign of Radian's Settings area, which currently mixes app-level preferences with harness-level configuration (name and default model, instruction prompts, a specialist agent roster, a skills and tools catalogue, a workflow graph editor, a project list, and a background curator) in a way the product owner describes as unsorted, cluttered and prone to overflow.

## Method and how to read this

Each app below is assessed against six dimensions: navigation model, how entity collections are handled, page anatomy, save model, progressive disclosure, and naming conventions. Claims are sourced inline to official documentation, help centres, changelogs or Apple's Human Interface Guidelines wherever a source could be fetched. Three confidence levels are used and named explicitly in the text:

- Unmarked claims are directly confirmed by a fetched primary source (the citation follows the claim).
- "Moderate confidence" means the claim came from a search-indexed excerpt of an official page that could not be fetched directly (several help centres, notably help.openai.com and support.discord.com, block automated fetches), so the wording is not independently verified against the live page.
- "Unverified (from general knowledge)" means no primary source could be found for the claim at all. These are flagged individually rather than silently smoothed over.

Product screenshots embedded in official docs count as primary sources. Nothing below should be read as a recommendation on its own; the synthesis at the end separates description from advice.

## Part A: multi-entity scoped settings

### Linear

**Navigation.** Full page, not a modal, reached by clicking the workspace name (top left) and selecting Settings ([Workspaces](https://linear.app/docs/workspaces)). The settings root has four top-level sections, in this order: **Account** ("Personal settings, notifications, and preferences"), **Features** ("Configuration for workspace-level features such as Initiatives, Customer requests, and SLAs"), **Administration** ("Workspace settings and configuration (admins only)"), **Your teams** ("A list of teams you're a member of and their settings") ([changelog, 18 Dec 2024](https://linear.app/changelog/2024-12-18-personalized-sidebar)). Scope is separated by section rather than by a modal or a separate app area: Account is personal, Features and Administration are workspace-wide, Your teams drills into a single team. There is no settings-search box; navigation runs through the global command menu (Cmd/Ctrl+K, or "O then S" from anywhere to jump to a settings page) ([Search](https://linear.app/docs/search)).

**Collections.** Your teams lists the teams you belong to; right-click a team to open **Team settings** ([Teams](https://linear.app/docs/teams)). A team's settings page shows a summary card per feature area first, then you open the specific card for the full configuration, a list-of-cards pattern rather than a persistent master-detail pane. Team sub-pages: General, Members, Issue labels, Templates, Recurring issues, Slack notifications, Issue statuses and automations, Triage, Cycles. Workspace-wide members sit at Settings > Administration > Members as a filterable, sortable table with a per-row overflow menu ("Change role..."). The 2024 redesign specifically converted admin lists into "data-rich table layouts" with per-column filter and sort.

**Page anatomy.** Each top-level section carries a one-line description under its label (quoted above); this is the clearest documented anatomy pattern for Linear. Column width and card layout are not documented; unverified.

**Save model.** No explicit save-bar language was found. Toggles use action verbs like "Turn on/off," consistent with autosave but not stated outright (unverified). One flow is explicitly staged: workspace deletion, below.

**Progressive disclosure.** A Danger Zone sits under Settings > Workspace > General for **Delete workspace**: the owner or admin initiates, Linear emails a confirmation code, the workspace is "scheduled for deletion in 48 hours," and any admin can cancel in that window. Team visibility (public or private) sits under a named **Access and permissions** sub-section ([Private teams](https://linear.app/docs/private-teams)). An admin-only API section covers OAuth apps and webhooks.

**Naming.** Plain, task-oriented labels throughout (Your teams, Issue labels, Recurring issues, Access and permissions), no internal jargon. One-line helper descriptions are confirmed at the top-level section labels.

### Discord

**Navigation.** Three separate, non-nested settings surfaces: **User Settings** (personal, gear icon near mute/deafen: My Account, Privacy & Safety, Authorized Apps, Connections), **Server Settings** (per server, opened from the dropdown beside the server name), and **Channel Settings** (per channel, cog icon on hover) ([Account Settings](https://support.discord.com/hc/en-us/categories/200404358-Account-Settings), [Channel Permissions Settings 101](https://support.discord.com/hc/en-us/articles/10543994968087-Channel-Permissions-Settings-101)). Discord's support site does not publish one ordered list of the Server Settings left-tab labels; reconstructed from individual articles, the tabs include Overview, Roles, Emoji, Widget, Server Templates, Members, and a Moderation group (Safety Setup: Rules Screening, Verification Level, AutoMod) ([AutoMod FAQ](https://support.discord.com/hc/en-us/articles/4421269296535-AutoMod-FAQ)). Whether the surface renders as a full-screen overlay or a distinct page is not stated in any fetched doc; unverified, though commonly observed as a full-screen overlay. No settings-search feature was found.

**Collections.** Roles: a list; clicking a role opens **Display**, **Permissions**, and **Manage Members** tabs, with hierarchy set by drag-reordering directly in the list ([Roles and Permissions](https://support.discord.com/hc/en-us/articles/214836687-Discord-Roles-and-Permissions)). Members: a dedicated Members tab, table form. Channels are not listed inside Server Settings at all; each channel has its own settings panel opened from the main sidebar, including its own Permissions tab. Discord therefore mixes list-inside-settings-then-drill-in (Roles, Members) with drill-in-from-outside-settings-entirely (Channels).

**Page anatomy.** Permission toggles are consistently paired with plain-language helper explanations (what "View Channel" or "Manage Threads" does). Broader layout specifics are not documented; unverified.

**Save model.** Role reordering and permission toggles read as instant-apply in every article, though no page states this outright (unverified but widely corroborated). Destructive actions instead use explicit confirmation, for example Transfer Ownership: "select the toggle to confirm and acknowledge the transfer" ([Transfer Ownership](https://support.discord.com/hc/en-us/articles/216273938-How-to-Transfer-Ownership-of-a-Discord-Server)).

**Progressive disclosure.** Moderation and safety settings are grouped behind a dedicated Safety Setup area rather than mixed into Overview. Whether destructive actions sit in a labelled "Danger Zone" is not documented.

**Naming.** Mostly plain (Roles, Emoji, Members, Server Templates), with one branded term used as a proper feature name rather than a generic description: **AutoMod**.

### GitHub

**Navigation.** Full page, not a modal, reached via a Settings tab on the repository or organisation page. A February 2022 redesign grouped repo, org, user and team settings into a labelled sidebar "for improved information architecture and discoverability" ([Redesign of GitHub's settings pages](https://github.blog/changelog/2022-02-02-redesign-of-githubs-settings-pages/)). Current repository settings sidebar groups: **General** (default tab, holds rename and the Danger Zone at the bottom), **Access** (Collaborators & teams), **Code, planning, and automation** (Pages, Rulesets, Webhooks, Environments), **Security & quality**, renamed from plain "Security" on 2 April 2026 (Advanced Security, Findings, formerly "Vulnerability alerts"; Security policy, formerly "Policy"; Code quality) ([changelog](https://github.blog/changelog/2026-04-02-the-security-tab-is-now-security-quality/)). Organisation settings are reached via avatar, Organizations, pick org, Settings; the same Access-section pattern repeats with a Member privileges item ([Accessing your organization's settings](https://docs.github.com/en/organizations/collaborating-with-groups-in-organizations/accessing-your-organizations-settings)). GitHub has recently split combined pages for clarity: SSO and Organizations became two distinct user-settings pages on 13 July 2026, and team management moved entirely into org Settings > Teams on 18 December 2025 rather than staying a separate top-level Teams tab. No general settings-search box was found; a scoped "Search repositories" filter exists on one org sub-page (the Advanced Security configuration table) but is not settings-wide.

**Collections.** The org's repository table, on the security-configuration sub-page, is a filterable list with free-text search and an Advanced filters dialog, used for bulk configuration rather than a classic drill-in ([Filtering repositories](https://docs.github.com/en/code-security/securing-your-organization/managing-the-security-of-your-organization/filtering-repositories-in-your-organization-using-the-repository-table)). Teams: org Settings > Teams lists teams, and each team has its own settings page; the exact list and drill-in UI were not confirmed in the fetched sources.

**Page anatomy.** General is the default tab and the canonical location of the Danger Zone at the very bottom of the page. Deletion requires: "I want to delete this repository," then "I have read and understand these effects," then typing the repository name, then "Delete this repository" ([Deleting a repository](https://docs.github.com/en/repositories/creating-and-managing-repositories/deleting-a-repository)). Feature-specific settings (Webhooks, Environments, Pages) are each their own full page from a single sidebar click, not tabs within one shared detail page.

**Save model.** No single documented model; behaviour differs per page. Toggles read as instant; destructive flows use multi-step typed confirmation. No evidence of a persistent unsaved-changes save bar.

**Progressive disclosure.** Danger Zone is the explicit, consistently named pattern for repository deletion, archiving and transfer, each gated by typing the repository name ([Archiving repositories](https://docs.github.com/en/repositories/archiving-a-github-repository/archiving-repositories)). Organisation-level equivalents (Archiving an organization, Deleting an organization account) are separate docs pages.

**Naming.** Mostly plain (General, Collaborators & teams, Webhooks, Environments, Pages). The security area's naming was recently simplified toward plainer language (Vulnerability alerts to Findings, Policy to Security policy, Security to Security & quality), a visible drift toward plainer naming over time.

### Vercel

**Navigation.** Full page, with two explicitly named scopes: "Team Settings: Any settings configured here, are applied at the team-level" and "Project Settings: These are specific settings for the selected project" ([Project settings](https://vercel.com/docs/project-configuration/project-settings)). A team switcher at the top left of the dashboard changes which team's projects are visible; selecting a project then enters project scope ([Accounts, "Switching teams"](https://vercel.com/docs/accounts)). Personal account settings form a third scope, reached via avatar then Settings, landing on `/account/settings` with sub-items such as Authentication. No dashboard-wide settings-search was found.

Project Settings sidebar, in the order given by the canonical doc's own structure: General; Build and Deployment; Domains; Environment Variables; Git; Integrations; Deployment Protection; Functions; Cron Jobs; Project members; Webhooks; Drains; Security; Advanced. Team Settings items confirmed, not necessarily exhaustive: General, Billing, Members, Security & Privacy.

**Collections.** Projects: a dashboard list; selecting one opens its own full settings sidebar (a persistent left-nav within project context, not literal browser tabs) ([Projects overview](https://vercel.com/docs/projects)). Domains: a list of rows within the Domains settings page, added via an "Add Domain" button that opens an inline input, with each row then showing live DNS-configuration status. Environment Variables were redesigned on 16 January 2026 specifically to reduce scrolling and add progressive disclosure between shared and project-level variables ([changelog](https://vercel.com/changelog/improved-environment-variables-ui)).

**Page anatomy.** Each settings page's title matches its sidebar label one to one. The General page holds: Project name, Project avatar, Build and development settings, Node.js version, Project ID (read-only, near the bottom of the page), and Vercel Toolbar settings. Environment Variables are key and value pairs, each scoped to Production, Preview, Development or Custom environments via checkboxes, with values up to 64KB.

**Save model.** Explicit, per-field Save buttons, directly documented several times: username, "enter your new username... Click Save"; avatar, "click Set Avatar"; default team, "press Save"; root directory, "Click Save to apply the changes" ([Accounts](https://vercel.com/docs/accounts), [Configuring a Build](https://vercel.com/docs/builds/configure-a-build)). Some settings apply only on the next deployment rather than immediately, an explicit note for Build and Root Directory changes.

**Progressive disclosure.** A dedicated Advanced section sits at the bottom of Project Settings (Directory Listing, Skew Protection). Team-level danger actions use individually named sections rather than one umbrella label: Leave Team, Delete Team. Read-only IDs (Project ID, Team ID) sit inline near the bottom of the relevant General page, not segregated to a separate About page.

**Naming.** Mostly plain (Domains, Environment Variables, Git, Functions, Cron Jobs), with some genuinely technical items surfaced directly at the top level rather than nested (Drains, OIDC Federation, Skew Protection).

### Notion

**Navigation.** Three explicit scopes named directly in the docs: **Account** (personal), **Workspace**, **Teamspace** ([Intro to workspaces](https://www.notion.com/help/intro-to-workspaces)). Entered by clicking the workspace name at the top of the sidebar (which switches workspace and also offers Settings), then Settings; some help pages label the sidebar entry "Settings & members" instead, likely a plan-tier or version difference. Whether the surface is a modal or its own full page with a URL is not stated. A settings-search box is documented and scope-aware: results show where the setting lives, for example "Workspace / General," and search matches a setting's name, its description, or the page it is on.

**Collections.** A Teamspaces table sits under Settings > Teamspaces (workspace owners only), with columns Owners, Members (expandable), Access (Open, Closed or Private, Private is Business or Enterprise only), and Updated (sortable) ([Manage teamspaces](https://www.notion.com/help/manage-teamspaces)). Drilling into a single teamspace's own settings happens via a row overflow menu (take ownership, archive, restore), not a separate detail page.

**Page anatomy.** Workspace > General, in the order given by the doc: Name, Icon, Trusted domain access, Export all workspace content, Export members as CSV, a "Save and display page view analytics" toggle, then a Danger zone at the end ([Workspace settings](https://www.notion.com/help/workspace-settings)). Visual layout details, label placement, column width, are not documented.

**Save model.** No Save button is quoted anywhere in the fetched docs. The settings-search behaviour, which jumps to and briefly highlights a setting, is consistent with instant-apply fields, but this is inferred rather than stated outright.

**Progressive disclosure.** A named Danger zone sits at the bottom of Workspace > General for workspace deletion. Plan-gating is quoted directly: "Many of these settings are only visible if you're an admin on a Plus Plan or Enterprise Plan. They don't appear in the mobile app at all." Teamspace settings use the same plan-gating pattern.

**Naming.** Generally plain (Name, Icon, Export all workspace content, Teamspaces), though "Trusted domain access" and "Identity" lean toward admin and IT jargon. No one-line helper-description pattern under each label was directly confirmed.

## Part B: AI and developer tools with models, rules, agents and tools

### Cursor

Documentation is thin here and mid-migration between two coexisting surfaces; several claims below are flagged accordingly.

**Navigation.** A classic "Cursor Settings" window (VS Code-style, opened with Cmd/Ctrl+,) with tabs including Models, Features (Model Context Protocol), Tab, Beta and Docs; an Indexing & Docs tab was hidden behind a server-side feature gate in 2026 ([forum bug report](https://forum.cursor.com/t/codebase-indexing-settings-tab-hidden-by-disable-codebase-indexing-feature-gate-please-re-enable/165859)). A newer, separate "Customize" page, shipped as v3.9 on 22 June 2026, consolidates Plugins, Rules, Skills, Subagents, Hooks, Commands and MCP servers in one place, with an explicit scope filter: "Filter by scope to see what is installed for you, your workspace, or your team" ([Customize Cursor](https://cursor.com/docs/customize-cursor)). Whether classic Settings opens as a modal or an editor tab, and whether settings search exists, is not confirmed by a Cursor-specific source; unverified.

**Collections.** Rules: list-then-drill-in-to-file. "Open Customize in the sidebar, go to Rules, and click Add Rule" creates a file under `.cursor/rules` with a type dropdown (Always Apply, Apply Intelligently, Apply to Specific Files, Apply Manually) plus YAML frontmatter ([Rules](https://cursor.com/docs/context/rules)). MCP servers: a list with enable and disable toggle switches, one-click install from a Marketplace, or hand-edited via `mcp.json` at global and per-project scope ([MCP](https://cursor.com/docs/context/mcp)). Notably, Cursor removed the Codebase Indexing settings page entirely in 2026 in favour of agentic grep search, a useful example of a collection being retired rather than accumulating.

**Page anatomy.** Rule files and MCP configs are ultimately files, edited via frontmatter or generated conversationally through a `/create-rule` command. Whether the Customize page renders them as inline forms or raw file views is not documented; unverified.

**Save model.** Unverified; no primary source states it explicitly.

**Progressive disclosure.** A Beta section covers early-access opt-in. The 2026 Indexing-tab removal was a server-side feature gate rather than a client-side Advanced toggle, disclosure enforced remotely rather than by a local setting.

**Naming.** Consistent, fairly technical vocabulary used as literal category names (Plugins, Rules, Skills, Subagents, Hooks, Commands, MCP servers). No one-line helper descriptions under each item were found.

### Claude desktop app

**Navigation.** Opened via initials or name (lower left), then Settings. Confirmed sub-pages: Appearance, Extensions (desktop-only), and an "Instructions for Claude" personalisation field ([Customizing your appearance settings](https://support.claude.com/en/articles/8887527-customizing-your-appearance-settings)). Connectors moved out of Settings entirely into a separate "Customize > Connectors" page, mirroring Cursor's split of preferences from extensibility ([Get started with custom connectors](https://support.claude.com/en/articles/11175166-get-started-with-custom-connectors-using-remote-mcp)). Organisation and workspace scope is a wholly separate admin surface (`claude.ai/admin-settings/...`). No settings-search evidence was found.

**Collections.** Connectors: a master list at Customize > Connectors, filterable by category, each entry showing a description, its capabilities, and a Connect or Install button; connected items can be disconnected or have permissions reviewed. Per-conversation enablement is a separate toggle reached from the composer's plus button, a configure-once-then-toggle-per-conversation pattern ([Use connectors](https://support.claude.com/en/articles/11176164-use-connectors-to-extend-claude-s-capabilities)). Extensions (local MCP packaging, desktop-only): Settings > Extensions > Browse extensions opens a directory; installing configures required settings such as API keys through the interface rather than hand-edited JSON ([Local MCP servers](https://support.claude.com/en/articles/10949351-getting-started-with-local-mcp-servers-on-claude-desktop)).

**Page anatomy.** Appearance is simple choice rows: Color Mode (Light, Match System, Dark), Chat Font (Default, Match System, Dyslexic Friendly). "Instructions for Claude" is an inline text field directly under Settings, not a modal; project-scoped instructions are a separate field.

**Save model.** Unverified; no fetched source states it explicitly.

**Progressive disclosure.** An "Advanced settings" click reveals an "Extension Developer" section for installing `.mcpb` files manually, a clean one-click-deep developer affordance. Session-security controls live entirely under the separate Organisation admin settings, not a collapsed section inside personal Settings.

**Naming.** A deliberate jargon split: locally installed MCP servers are called **Extensions** ("as easily as browser extensions"), while hosted or remote integrations are called **Connectors**, two consumer-friendly names for the same underlying protocol, split by deployment model. "Instructions for Claude," not "system prompt," is similarly plain.

### Claude Code

The best-documented of the AI tools surveyed.

**Navigation.** No traditional settings GUI; configuration is JSON files surfaced through slash commands. `/config` lists a short set of personal options (theme, editor mode, verbose output), explicitly "not every settings key." `/status` shows a read-only list of every settings file that loaded. `/permissions`, `/mcp`, `/memory` and `/agents` each open a dedicated view for one collection ([Settings](https://code.claude.com/docs/en/settings)). Scope precedence is the most rigorously documented of any app in this survey, five tiers:

| Scope          | File                        | Affects            |
| -------------- | --------------------------- | ------------------ |
| Managed        | managed-settings.json       | Whole org          |
| Command line   | --settings flag             | This session       |
| Project local  | .claude/settings.local.json | You, this project  |
| Shared project | .claude/settings.json       | Team, via git      |
| User           | ~/.claude/settings.json     | You, every project |

In Claude Desktop's "Code" tab, rebuilt 14 April 2026, per-session configuration lives inline in the session toolbar (Environment, Project folder, Model, Permission-mode dropdowns), not a settings page; app-level preferences sit separately under Settings > Claude Code ([Desktop](https://code.claude.com/docs/en/desktop)).

**Collections.** MCP servers (`/mcp` panel): a list with live per-row status glyphs (Connected, Needs authentication, Failed to connect, Pending approval, Disabled for this project) plus tool count and cache age; clicking a server drills into URL, command and header detail ([MCP](https://code.claude.com/docs/en/mcp)). This is the strongest list-with-live-status master-detail pattern found anywhere in this survey. Subagents: Markdown files with YAML frontmatter under `.claude/agents/` (project) or `~/.claude/agents/` (user); `/agents` no longer opens a creation wizard, removed in v2.1.198, and instead prints a reminder to ask Claude to write or edit the file directly, an explicit choice to keep this collection in conversational or file editing rather than GUI forms ([Subagents](https://code.claude.com/docs/en/sub-agents)). Rules and memory: one topic per Markdown file under `.claude/rules/`, optionally scoped to matching paths; `/memory` lists every CLAUDE.md and rules-file location across scopes and opens the chosen one in your editor.

**Page anatomy.** Every long-text artefact (CLAUDE.md, rule bodies, subagent prompts) opens as a plain file in your own editor, never an inline textarea or modal, a categorically different approach from every other app in this survey.

**Save model.** File-based. Settings files are hot-reloaded: "Claude Code watches your settings files and reloads them when they change... without a restart," with a short, named list of exceptions requiring a restart. `/config` selections save immediately on choice.

**Progressive disclosure.** The scope stack itself is the disclosure model, from Managed (invisible and non-overridable to the end user) down to User (personal and global). A short table of named exceptions documents where a stricter lower-scope value still beats a looser managed one, a precisely specified security-floor pattern. Diagnostics (`/status`, `claude doctor`) sit one command away rather than shown inline by default.

**Naming.** Deliberately technical (CLAUDE.md, settings.json, mcpServers, `Bash(npm run build)` rule syntax), appropriate for a CLI surface, but re-labelled consistently wherever the same concept surfaces in a friendlier host UI: permission mode "default" is "labelled Manual in the CLI, the VS Code and JetBrains extensions, and the desktop app," one technical key, one consistent friendly label across every embedding ([Permissions](https://code.claude.com/docs/en/permissions)).

### ChatGPT desktop app

help.openai.com blocked direct fetches; findings below combine a fetchable secondary docs site (learn.chatgpt.com) with search-indexed excerpts of help.openai.com, flagged by confidence.

**Navigation.** Opened via the profile icon (top right), then Settings, or Cmd/Ctrl+,. The desktop app merged Codex into ChatGPT on 9 July 2026, creating three modes, Chat, Work and Codex, switched via a dropdown above the composer rather than inside Settings ([Quickstart](https://learn.chatgpt.com/docs/quickstart?setup=app)). The full current settings tree, directly fetched: General, Profile, Keyboard Shortcuts, Notifications, Appearance, Pets, Browser, Computer Use, Personalization, Suggested Prompts, Memories, Archived Chats, "Keep a Chat Near Your Work" ([Settings reference](https://learn.chatgpt.com/docs/reference/settings)). Per-project configuration for Codex mode lives in `config.toml` files at user and project scope, with an explicit list of keys a project file cannot override (provider, auth, telemetry), structurally similar to Claude Code's managed and user split. Enterprise and admin scope is entirely separate URLs (`chatgpt.com/admin/...`), not a Settings tab. No settings-search evidence was found.

**Collections.** Apps/Connectors: renamed from "Connectors" to "Apps" on 17 December 2025 "to present a more unified experience" (moderate confidence), each with a Connect button. MCP servers, Codex mode: a config-file collection under `mcp_servers.<id>`, with a GUI toggle also present in Developer Settings ("Integrations and MCP") ([Developer settings](https://learn.chatgpt.com/docs/developer-settings)). Archived chats and shared links each have a Manage button that drills into a dated sub-list (moderate confidence).

**Page anatomy.** Custom Instructions sit behind an "Enable customisation" toggle; once on, newer UI adds structured fields (preferred name, profession, a chip-style multi-select of "traits") beyond a single freeform box (moderate confidence). Data Controls uses a consistent row-label-plus-action-button layout; the most severe row, Delete account, requires typing the word DELETE (moderate confidence, not independently fetched). Developer Settings, the Codex surface, is the single most directly comparable page to a coding-agent tools and permissions surface found anywhere in this survey: Project and terminal behaviour, Code review delivery mode, IDE-context sync, Git (branch naming, force-push, PR templates), Integrations and MCP, Browser developer mode.

**Save model.** Largely unverified against a primary source.

**Progressive disclosure.** Data Controls stacks severity from a training-data toggle up to account deletion on one page, the deletion gated by a typed-word confirmation (moderate confidence). Admin and enterprise controls are fully out of band on separate URLs rather than a collapsed section inside personal Settings.

**Naming.** "Apps," replacing "Connectors," and "Data Controls," not "Privacy," are plain, consumer-oriented renames with an explicit unification rationale (moderate confidence). The Developer Settings layer keeps raw technical vocabulary (config.toml, sandbox_mode, approval_policy, CDP, MCP), the same friendly-outer, technical-inner split seen in Claude Desktop and Claude Code.

### Warp

**Navigation.** Opened via Cmd/Ctrl+, or a `warp://settings` URI; whether the default surface is a modal or a persistent tab is not stated ([Settings file](https://docs.warp.dev/terminal/settings/)). Destinations referenced across docs, never shown as one enumerated list: Appearance; Keyboard shortcuts; Privacy; Agents > Profiles; AI > Agents > Permissions (the docs use both phrasings inconsistently); Agents > Warp Agent (a global AI on/off toggle). The underlying `settings.toml` groups as `[general]`, `[appearance]`, `[agents]`, `[terminal]`, `[privacy]`. A search bar is confirmed for Keyboard Shortcuts specifically, not confirmed settings-wide. There is no project or workspace settings scope; Warp's project-like concepts, Launch Configurations and Tab Configs, live outside Settings entirely. Settings Sync propagates settings across machines under a Warp account.

**Collections.** Agent Profiles: a true collection, multiple profiles editable under Settings > Agents > Profiles; every user starts with a default profile, and new profiles copy it as a starting point; each profile carries name, base model, autonomy, and a nested Permissions sub-section ([Agent Profiles & Permissions](https://docs.warp.dev/agents/using-agents/agent-profiles-permissions)). MCP servers are handled via allowlist and denylist regex rules rather than a browsable list UI in the docs. Keybindings: a flat searchable list with inline conflict highlighting, an orange border on conflicting binds, not drill-in.

**Page anatomy.** Not documented explicitly; the `settings.toml` nesting implies grouped UI sections but this is inference from file structure rather than a described UI.

**Save model.** Not documented; the bidirectional `settings.toml`-and-panel relationship implies instant save, but no page states this outright.

**Progressive disclosure.** A free-tier privacy toggle is plan-gated: "telemetry must be enabled to use AI features on the Free plan" ([Privacy and data control](https://docs.warp.dev/support-and-community/privacy-and-security/privacy/)). Agent autonomy has an explicit extreme tier: "Run until completion ignores the denylist entirely and is the purest form of 'YOLO' mode," a genuine documented danger-zone-style setting ([Agent Permissions](https://docs.warp.dev/agents/autonomy/agent-permissions)). No documented catch-all Advanced section.

**Naming.** Plain labels (Privacy, Keyboard shortcuts, Appearance, Profiles, Permissions), with one internally technical term used as an actual product term, "YOLO mode," alongside the more neutral "Always allow." Helper text is confirmed at the field level, for example Base model described inline as "The core engine for your Agent."

### Zed

**Navigation.** A deliberate choice of a separate window rather than a tab, explained on Zed's own engineering blog: the team debated "a separate window like in most native apps vs. a tab like in many web based applications (like VS Code)" and chose the window because "settings have their own sense of location" distinct from the active project workspace ([How We Rebuilt Settings in Zed](https://zed.dev/blog/settings-ui)). Layout is categories on the left, controls on the right. The AI settings path is `zed: open settings`, then AI in the sidebar (or the `agent: open settings` command directly); under AI, a General section holds three sub-pages: LLM Providers, External Agents, MCP Servers ([Agent Settings](https://zed.dev/docs/ai/agent-settings)). A live search-as-you-type box is documented: "as you type in the search box, matching settings appear with descriptions and controls" ([Configuring Zed](https://zed.dev/docs/configuring-zed)). Scope is two first-class typed structures, `UserSettings` (global, `~/.config/zed/settings.json`) and `ProjectSettings` (per-project, `.zed/settings.json`), framed spatially in the blog: "User settings apply to everything, project settings interact with those user settings but apply to their own subset of files."

**Collections.** MCP, "context," servers have a dedicated list UI at Settings > AI > MCP Servers; Add Server offers Install from Extensions, Add Local Server, or Add Remote Server; installed servers show an inline status dot, green with a tooltip reading "Server is active," rather than a separate detail pane. LLM Providers and External Agents are each their own drill-in sub-page with Configure and Uninstall row actions. Language servers remain JSON-only under the `lsp` key with no dedicated visual list, an inconsistency worth flagging: some collections got a UI, others did not.

**Page anatomy.** A documented hybrid: "items that end with 'settings' can be configured via the Settings UI," others remain JSON-only, "settings file." Long text and edge-case parameters, for example `agent.commit_message_instructions` or per-model temperature arrays, are edited by opening the real `settings.json` in Zed's own editor, including a read-only "default settings" reference copy explicitly not meant to be edited.

**Save model.** Explicitly instant and auto-save, the clearest such statement found in the whole survey: "changes save automatically to your settings file" as you edit in the Settings Editor.

**Progressive disclosure.** Provider API keys are stored in the system keychain rather than as plaintext in `settings.json`, a security-motivated disclosure difference ([AI Quick Start](https://zed.dev/docs/ai/configuration)). A top-level kill switch, `"disable_ai": true`, is exposed both as a JSON key and a Settings Editor toggle rather than buried.

**Naming.** More technical and internal than the other AI tools surveyed: "context servers," Zed's term for MCP servers, and "External Agents" for ACP-integrated third parties, rather than plainer alternatives. The all-settings reference is organised by literal field names in Title Case (Buffer Font Fallbacks, Diagnostics Max Severity, Direnv Integration), reading as internal rather than task-oriented. Each entry does carry a one-line description alongside its name, default and options.

### Windsurf

All `docs.windsurf.com` URLs redirect to `docs.devin.ai` during this research, reflecting Windsurf's absorption into Cognition's product line; content sometimes reads "Devin Desktop" internally even under the windsurf.com URL. Treat this app's findings as the most time-sensitive in the survey.

**Navigation.** Settings root is accessed via a bottom-right control, documented under both "Windsurf Settings" and, in redirected pages, "Devin Settings." No single enumerated master list was found; confirmed fragments include a Cascade section (with an "Enable Sounds for Cascade" toggle, confirming Cascade as a real settings section) and an Advanced section (Cascade Gitignore Access, Agent Diff Zones, SSH Support, Dev Containers, WSL Beta, an Extension Marketplace URL) ([Advanced, redirects to docs.devin.ai](https://docs.windsurf.com/windsurf/advanced)). Rules are reached not via the gear-icon Settings surface at all but via a "Customizations" button inside the Cascade chat panel itself, with separate `+ Global` and `+ Workspace` creation buttons, two tiers: Global Rules for every workspace, Workspace Rules for the current project. Model selection is notably not a Settings feature at all; it is a dropdown embedded directly in the chat input, a meaningful divergence from every other AI tool surveyed. No settings-search evidence was found.

**Collections.** MCP servers: an "Add Server" flow (stdio, HTTP or SSE, possibly OAuth) plus a "View Raw Config" button that opens the underlying `mcp_config.json` directly, and a documented hard cap of 100 active tools across all MCP servers combined. Rules and Memories: a list with `+ Global` and `+ Workspace` add actions; editing an existing item is "click into it and then click the Edit button," a drill-in pattern whose exact edit surface was not confirmed. Hard size limits are documented precisely: global rules capped at 6,000 characters, workspace rule files capped at 12,000 characters each. Memories, auto-captured by the agent during conversations and stored internally, not version-controlled, are explicitly distinguished from Rules, which are user-authored and version-controllable.

**Page anatomy.** Not documented in any fetched source.

**Save model.** Not documented for the Settings UI generally; unverified.

**Progressive disclosure.** A confirmed, explicitly named Advanced section covers power-user and infrastructure settings (SSH, Dev Containers, WSL Beta, gitignore access, diff zones). Beta labelling happens inline on a setting's name, "WSL (Beta)," rather than a quarantined section. Rule character-limit caps function as an implicit guardrail.

**Naming.** A mix of plain and brand-specific jargon: "Cascade," the agent's brand name, is used as an actual settings-section label rather than a generic term like "Agent," and "Customizations" is an abstract umbrella label for what is functionally "AI behaviour rules." Raw-config escape hatches are named plainly, "View Raw Config."

### Raycast

The best-documented of the four editor and launcher tools for pure settings IA ([Settings](https://manual.raycast.com/settings)).

**Navigation.** A separate Preferences window, opened via Cmd/Ctrl+, or by typing "Settings" in root search. Confirmed full tab order: Account, General, Launcher, Shortcuts, Keyboard, Advanced, Organizations (conditional, Teams plan only), About, AI, Applications, then individual Extensions entries appended after the fixed tabs. Search is confirmed, global, and the broadest scope found in the survey: "Press Cmd+F/Ctrl+F while Settings is open and search for anything: a setting, a command, an extension, or just a keyword you remember." There is no project or workspace scope, since Raycast is a system launcher; the closest analogue, Organizations, separates personal configuration from a Teams or shared context.

**Collections.** Extensions is the clearest master-detail example in the whole survey: "each installed extension appears as its own entry in the sidebar, where you can select any extension to manage its preferences, authenticate with third-party services, enter access tokens, and assign shortcuts to its commands." Confirmed present since v1.9.0 ([changelog](https://www.raycast.com/changelog/1-9-0)) and current today. Extension preference field types, from the developer manifest reference: textfield, password with secure entry, checkbox, dropdown, appPicker, file, directory ([Manifest reference](https://developers.raycast.com/information/manifest)). The same preferences surface is reachable both by browsing Settings > Extensions and by an in-context "Configure Command" or "Configure Extension" action from the command itself. AI Extensions, tools the AI can call, reuse the same Extensions master-detail surface rather than a separate AI-only list.

**Page anatomy.** General tab: Open at Login, Show in Menu Bar, Raycast Hotkey (a key recorder control), an Appearance group (Follow System Appearance, Interface Size, Window Mode). The AI tab has a multi-sub-pane structure: Models & Providers (default model per surface, Subscriptions, API Keys, Custom Providers via a `providers.yaml` file, Local Models, a "Manage Models" picker), Agents/AI Commands/AI Extensions management, Projects, Personalization (Profile and Memory), Chat settings, Tools permissions ([AI](https://manual.raycast.com/ai)). Custom AI provider configuration explicitly drops to a config file rather than an inline form.

**Save model.** No explicit statement was found; the total absence of any Save or Apply language across the docs is consistent with instant save, an inference rather than a confirmation.

**Progressive disclosure.** An explicitly named Advanced tab acts as a catch-all (Window Activation Behaviour, Favicon Provider, Export & Import Settings, proxy and certificate connection settings). The Shortcuts tab is itself a read-only, filterable bird's-eye index of every assigned shortcut, not an editing surface. Platform-conditional settings are labelled inline, "(Windows-only)," "(Mac-only)," rather than hidden. The Organizations tab is plan-gated, shown only for Teams users.

**Naming.** Overwhelmingly plain and task-oriented (Open at Login, Show in Menu Bar, Follow System Appearance, Pop to Root Search, Fallback Commands). AI surfaces are deliberately disambiguated rather than folded into one generic "AI" bucket: Quick AI, AI Chat, AI Commands and AI Extensions are each named and kept separately discoverable.

## Part C: platform conventions

### macOS System Settings and Apple HIG

**Navigation.** The HIG's prescribed pattern for third-party apps is a dedicated auxiliary window, opened via the app's Settings menu item (App menu, Cmd+,), containing a toolbar of buttons that switch between panes, each pane holding a group of related settings; the window title updates to the visible pane's name, the window "accommodates the size of the current pane" rather than being freely resized, and reopening restores the most recently viewed pane ([Settings](https://developer.apple.com/design/human-interface-guidelines/settings)). An important divergence: Apple's own System Settings app, macOS 13 and later, does not follow this toolbar-of-panes idiom; it uses a full, resizable single window with a scrollable sidebar list instead ([System Settings](https://support.apple.com/guide/mac-pro/system-settings-apda966cb8af/mac)). Search is confirmed and prominent: "use the search field... Results appear in the sidebar as you type," with a "most often used" suggestion set shown on focus before typing, and clicking a result can jump straight into a sub-dialog ([Mac Help](https://support.apple.com/en-my/guide/mac-help/mchl8d10839d/mac)). No primary source enumerates the exact current sidebar label order as text; any specific ordered list should be treated as unverified.

**Collections.** Per-app settings for ordinary, non-system apps are explicitly not absorbed into System Settings: "To change options for an app, such as Mail or Safari, open the app, click the app's name in the menu bar, then choose Settings" ([Change system settings](https://support.apple.com/guide/mac-help/change-system-settings-mh15217/mac)). Privacy & Security's per-app permission lists are the one place System Settings itself surfaces a live collection of apps; the touchpoint is confirmed but its row-level visual anatomy is not documented and is treated as unverified. The general grouping principle from HIG Layout: "Group related items... using negative space, container shapes, or separator lines... Use progressive disclosure... disclosure triangles, menus, or nested views to reduce how much content to initially display" ([Layout](https://developer.apple.com/design/human-interface-guidelines/layout)).

**Page anatomy.** Window sizing is content-driven under HIG's settings-window guidance, a divergence from the shipping, resizable System Settings app. General layout principles that do apply: "Order content by relative importance... place the most important items near the top and leading side," and "Align elements to make them easier to scan, and use indentation to convey hierarchy." A commonly cited pixel-level label-left, control-right two-column specification comes from a third-party design reference, not from Apple directly, and is flagged as unverified from a secondary source. Controls: the HIG specifies switches, checkboxes and radio buttons belong "in the window body, not the window frame" ([Toggles](https://developer.apple.com/design/human-interface-guidelines/toggles)).

**Save model.** No primary-source text states "instant apply, no Save or Cancel" outright. This is consistent, observable macOS behaviour but is not confirmed by a direct Apple quote; unverified.

**Progressive disclosure.** Directly on point from HIG Layout: "Use progressive disclosure to make layouts cleaner and easier to interact with... Use disclosure triangles, menus, or nested views to reduce how much content to initially display; or use scrollable sections." HIG Sidebars caps hierarchy depth: "In general, show no more than two levels of hierarchy in a sidebar" ([Sidebars](https://developer.apple.com/design/human-interface-guidelines/sidebars)). No documented "Advanced" toggle or "danger zone" pattern exists specifically for macOS settings.

**Naming.** The HIG's settings guidance is explicit and directly quotable on restraint: "Minimize the number of settings you offer... too many settings can make the experience feel less approachable, while also making it hard to find a particular setting." "Avoid using settings to ask for setup information you can get in other ways." "Respect people's systemwide settings and avoid including redundant versions of them in your custom settings area." The menu item is literally labelled "Settings...," not "Preferences...". Rather than a persistent one-line description under every control, macOS relies on a separate Help button per option: "users can click the Help button for more information about the options," a genuine and useful contrast to VS Code's approach, worth calling out for Radian.

### VS Code Settings editor

A single, very complete primary source: [User and workspace settings](https://code.visualstudio.com/docs/getstarted/settings).

**Navigation.** Opens "in a modal overlay on top of the editor area" by default, configurable via `workbench.editor.useModal`, through File > Preferences > Settings, the Command Palette, or Cmd/Ctrl+,. The left side is a tree table-of-contents grouping settings into logical categories, with a "Commonly Used" group pinned at the top. Scope is two explicitly labelled tabs, confirmed by screenshot alt text: **User** and **Workspace**. Remote and multi-root Folder scopes exist in the live product when relevant but are not shown as always-present tabs in this doc. Precedence order, distinct from tab order, is Default, User, Remote, Workspace, Workspace Folder, each with language-specific variants, then Policy, which always wins. Search is live filtering as you type, with a filter button exposing `@`-prefixed query operators typed into the same box: `@modified`, `@ext:<id>`, `@feature:<name>`, `@haspolicy`, `@id:<settingId>`, `@lang:<id>`, and tag filters `@tag:advanced`, `@tag:experimental`, `@tag:preview`, `@tag:accessibility`, `@tag:workspaceTrust`. A deep-link URL scheme, `vscode://settings/<settingName>`, opens straight to a specific setting from outside the app.

**Collections.** Extension-contributed settings are grouped under an Extensions node in the left tree, "those settings are visible under an Extensions section," a tree-group-then-filtered-list pattern rather than list-then-drill-in. The same data is also reachable from the Extensions view's own "Feature Contributions" tab, so VS Code deliberately offers the same collection from two navigation paths, the global settings tree and the entity's own detail view.

**Page anatomy.** A two-pane layout: the TOC tree on the left, a vertical list of settings on the right for the selected category, each rendered as title, then description text, then the control. This is confirmed more by screenshot evidence than by explicit prose. A modified setting shows "a colored bar on the left... similar to modified lines in the editor," confirmed blue by screenshot alt text. A per-setting gear icon, Shift+F9, opens a context menu: reset to default, copy setting ID, copy JSON name-value pair, copy settings URL. Some settings cannot be edited in the UI at all and show an "Edit in settings.json" link inline instead. `settings.json` itself is a first-class parallel surface, an ordinary editor tab with IntelliSense and validation, not a fallback; a preference can make Cmd/Ctrl+, always open raw JSON instead of the GUI.

**Save model.** Explicitly instant-apply: "VS Code applies changes to settings directly as you change them," with no Save, Apply or Cancel button anywhere. Unsaved state is tracked relative to default, not relative to disk, and surfaced two ways: the inline blue bar per row, and a literal named filter, `@modified`, "A setting shows up under this filter if its value differs from the default value, or if its value is explicitly set in the respective settings JSON file." Reset is per-setting via the gear menu, or bulk by editing `settings.json` directly, with an explicit warning that there is no recovery.

**Progressive disclosure.** Advanced settings are hidden from default search results: "By default, advanced settings are hidden from search results unless you use the `@tag:advanced` filter," reversible via a `workbench.settings.alwaysShowAdvancedSettings` preference. A maturity-badge system doubles as disclosure: Experimental (may change or be removed, filterable `@tag:experimental`), Preview (final functionality still being iterated on, usually disabled by default, filterable `@tag:preview`), and Stable (no badge). There is no literal "danger zone" section; destructive actions, such as a full `settings.json` reset, are called out with inline warning prose instead.

**Naming.** The UI structurally forces a title-plus-one-line-description per setting as the base unit, distinct from the underlying dotted JSON key, for example `workbench.colorTheme` versus its display title. The gear menu's "copy setting ID" and "copy JSON name-value pair" actions exist precisely because the human label and the internal key are different things people need to move between. Settings IDs are namespaced by contributing area (`editor.*`, `workbench.*`, `files.*`, extension IDs), the internal, jargon layer, while the docs themselves recommend searching by the human-recognisable name, an extension's name rather than its ID, as the primary route.

### Slack Preferences

**Navigation.** Two full-page, non-modal surfaces reached from the same menu: click the workspace or org name (top left), hover "Tools & settings," then choose Workspace settings (an admin dashboard, or a workspace-scoped page for single-workspace admins) or Organization settings (Enterprise Grid, org-wide) ([Guide to the Slack admin dashboard](https://slack.com/help/articles/115005594006-Guide-to-the-Slack-admin-dashboard)). The admin dashboard's left sidebar, exact labels and order: Organization, People, Channels, Slack Connect, Billing, Analytics, Security, Settings. Scope separation is explicit in the copy: "anything you configure in the admin dashboard will apply to every workspace in your org," while per-workspace management is a distinct linked page. Separately, non-admin workspace customisation (name, icon, description, URL) lives under Tools & settings > Customize [workspace name]. Personal settings are separate again: profile picture, then Preferences, with tabs including Notifications. No dedicated settings-search box was found in the admin dashboard docs.

**Collections.** Channel management is a searchable list at Workspace settings > Channels, with a per-row three-dot overflow menu for bulk-style actions. A single channel's own settings are instead reached in context, from the channel header itself: channel name, then Settings, containing actions like "Archive channel for everyone" and "Delete channel." Apps: Tools & settings > Manage apps opens the Slack App Directory, with a distinct "App Management Settings" item in its own left column. The overall pattern is list or table (Channels, Apps, People) with inline overflow-menu actions, plus separate in-context Settings entry points reached from the entity itself, not a persistent two-pane master-detail.

**Page anatomy.** The clearest documented example is the standalone "Review your workspace's settings" page: a page title plus a one-line description, "The Workspace Settings page keeps details transparent...," followed by grouped read-only info: Primary Owner contact, "the Customer" identity, message and file retention policy, Export and Discovery API availability, and, Enterprise Grid only, custom Terms of Service.

**Save model.** An explicit "Edit... then Save or Update" pattern is documented repeatedly rather than continuous autosave, for example posting permissions ("Select the Settings tab, then click Edit next to Posting permissions"), the enterprise search toggle ("check or uncheck the box... and click Save"), and channel descriptions ("hover over Description and click Edit... enter a channel description and click Update description").

**Progressive disclosure.** Destructive actions sit behind an in-context Settings entry on the entity, then a two-step confirmation: channel deletion requires selecting "Delete this channel," then explicitly checking "Yes, permanently delete the channel" before the delete button activates, with an explicit warning ("Deleting a channel is permanent, so make sure to proceed with care"). Workspace deletion is restricted to the Primary Owner only; the full confirmation flow beyond that restriction was not retrievable and is unverified in detail. Read-only info is consolidated on a separate informational page rather than inline in the admin dashboard.

**Naming.** A mix of plain task labels (Manage apps, Delete a channel, Adjust channel management permissions) and Slack-specific product terms used as category labels (Slack Connect, Channel Managers). Admin dashboard top-level categories (Organization, People, Channels, Billing, Analytics, Security, Settings) are plain and domain-oriented rather than jargon-heavy. No explicit one-line helper text under a settings label was directly quoted in the fetched sources; unverified, though visually characteristic of the product.

## Synthesis

### Recurring structural patterns

1. **Scope is separated by a switcher outside the settings tree, not a tab inside it.** The user chooses which workspace, team, org or personal account before entering settings, and that choice persists as page furniture rather than living as one more settings section. Vercel (team switcher), Linear (workspace switcher plus a distinct Your teams section), Notion (workspace switcher), Slack (workspace and org menu), GitHub (avatar to switch personal and org scope, then a repository's own Settings tab), Discord (three separate, non-nested settings surfaces for user, server and channel).

2. **Container-level settings are entered by first navigating to the entity, then finding its own Settings**, rather than one global screen holding every entity's fields at once. GitHub (a repository's own Settings tab), Slack (a channel's own Settings from its header), Vercel (select a project, then its Settings sidebar), Zed (per-project settings file distinct from user settings).

3. **Collections of same-shaped entities default to a list or table, then drill in to a dedicated detail page**, not a persistent two-pane master-detail. Linear (Your teams to team settings sub-pages), GitHub (repository and team tables), Notion (Teamspaces table with a row overflow menu), Slack (Channels, Apps and People tables).

4. **Persistent master-detail, list pane and detail pane both visible at once, is the exception**, reserved for homogeneous collections that benefit from quick scanning and comparison. Raycast Extensions (confirmed since v1.9.0, still current), Zed's MCP Servers list with an inline status dot, Claude Code's `/mcp` panel with live per-row status glyphs.

5. **A named "Danger Zone," or an equivalent, sits at the bottom of the relevant page for destructive actions**, distinct from ordinary settings. GitHub (Danger Zone, bottom of repository General), Notion (Danger zone, bottom of Workspace General), Vercel (individually named sections instead of one umbrella label: Leave Team, Delete Team).

6. **Destructive actions require friction proportional to their blast radius.** Linear (an emailed confirmation code plus a 48-hour delay before workspace deletion), GitHub (typing the repository name before Delete, Archive or Transfer), Slack (checking a literal "Yes, permanently delete" box before the delete button activates), ChatGPT reportedly (typing DELETE for account deletion, moderate confidence).

7. **Power-user or rarely-needed configuration drops to a raw file, with the GUI covering the common path only.** Zed (`settings.json`, plus a read-only default-settings reference copy), Warp (`settings.toml`, a separate keysets repository for advanced keybindings), Windsurf (`mcp_config.json` via a "View Raw Config" button), Raycast (`providers.yaml` for custom AI providers), Cursor and Claude Code (rule and agent files with YAML frontmatter, edited in your own editor rather than an inline textarea).

8. **Save behaviour is mostly instant per field for ordinary settings, but an explicit Save reappears for named, consequential fields.** Vercel (repeatedly documented explicit Save buttons per field, with some changes stated to apply only on the next deployment), Slack (an Edit-then-Save-or-Update pattern for permissions and descriptions), Zed and VS Code (both explicitly instant, no Save button at all). No app surveyed documents a single page-level unsaved-changes bar summarising many fields at once; the closest documented analogue is VS Code's per-row modified indicator plus its `@modified` filter, which is per-setting, not per-page.

9. **Progressive disclosure is structural, a named section or a search filter, not just smaller text.** Raycast (an Advanced tab), Windsurf (an Advanced section), Cursor (a Beta section, plus server-side feature gating), VS Code (advanced settings hidden from search results by default, revealed by an `@tag:advanced` filter, plus Experimental and Preview maturity badges), Apple HIG (explicit guidance to use disclosure triangles and nested views, and to minimise the number of settings offered at all).

10. **Read-only identifiers and metadata sit inline near the fields they relate to**, not exiled to a separate About page. Vercel (Project ID and Team ID at the bottom of each entity's own General page), Slack (a dedicated but still workspace-scoped "Review your workspace's settings" summary page).

11. **Naming is plain at the outer, consumer-facing layer, with technical vocabulary pushed to an inner Developer or Advanced layer, or kept as an internal key distinct from the label a person reads.** Claude Code (one technical permission-mode key, "default," consistently relabelled "Manual" in every host UI), Claude desktop (Extensions versus Connectors as two friendly names for one underlying protocol, split by deployment model), GitHub (an active drift toward plainer security-tab naming through 2026), VS Code (a human title and description for every setting, with the dotted internal key one click away), ChatGPT ("Apps" replacing "Connectors," "Data Controls" instead of "Privacy"). The clearest counter-example is Zed, whose top-level vocabulary, "context servers," Title Case field names like "Buffer Font Fallbacks," stays close to the internal implementation.

12. **A section or top-level label is followed immediately by a one-line, plain-language description of what it contains.** This is most consistently documented for whole sections rather than individual fields. Linear (a one-line description under each of the four top-level sections), VS Code (title, then description, then control, for every individual setting, the densest application of this pattern in the survey), Slack (a one-line description under the "Review your workspace's settings" page title).

### Anti-patterns to avoid

- A single flat settings list mixing personal, workspace and per-entity fields with no scope separation. Every app surveyed avoids this; it is essentially Radian's stated current problem.
- Putting the scope switcher, which workspace, team or harness is being configured, inside the settings tree itself as just another item to click through, rather than as persistent chrome above or outside the tree. Every app in Part A keeps the switcher outside settings.
- Showing every field for a dense entity type, an agent with a long system prompt, a project with planning documents and a memory ledger, on one long scrolling page instead of splitting into sub-pages or a list-then-drill pattern. GitHub, Linear and Vercel all split a container's settings into a labelled sidebar of sub-pages rather than one page.
- Surfacing internal implementation names, JSON keys, database columns, internal feature-flag names, as the primary label with no plain-language layer. Zed is the one clear counter-example found in this survey and is called out above; contrast with Claude Code's deliberate key-to-label translation.
- No confirmation, or only a generic "Are you sure?", on irreversible actions. Every app that documents deletion uses friction proportional to the action: typed names, checkboxes, delays or emailed codes.
- Offering power-user configuration through only one channel: GUI-only with no escape hatch, or file-only with no GUI path, for the same feature. The recurring pattern is offering both, a GUI for the common path and a visibly linked file or JSON escape hatch (a "View Raw Config" or "Edit in settings.json" affordance) for the edge case, not two disconnected ways to configure the same thing.
- Collapsing distinct scopes, for example personal preferences and settings that affect an entire team, onto the same page without a clear boundary. Notion's explicit plan-gating language and Slack's separate admin-dashboard-versus-workspace-page split both exist specifically to prevent this confusion.

### Recommendation for Radian

Given the shape described, an app scope plus one or more harness containers, and within a harness a set of dense entity collections (specialists, skills and tools, workflows, projects, curator), no single surveyed app is a complete template, but two combine into a close fit.

Use **Vercel's team-scope and project-scope split** as the outer model: a persistent switcher, outside the settings tree, in the app's own chrome rather than a settings tab, chooses between App and a named harness, matching the two-flat-groups plan already noted for Radian's settings restructure. Once a harness is selected, give it its own grouped sidebar in the Vercel or GitHub style, one label per entity type (General, Instructions, Specialists, Skills & Tools, Workflows, Projects, Curator), each its own page rather than one long scroll, with a Danger Zone at the bottom of the harness's General page for anything destructive, deleting the harness, wiping curator history.

For the entity collections within a harness, match the pattern to entity density rather than using one collection pattern everywhere:

- **Specialists** (name, model, prompt, tools, skills, a handful of fields per row) fit **Raycast's or Claude Code's persistent master-detail**: a scannable list on the left (name plus a model badge), full detail (prompt, tools, skills) on the right, so switching between specialists does not require a full page reload. This is the pattern Claude Code uses for MCP servers and Raycast uses for Extensions, both explicitly confirmed to keep a list and a detail pane on screen together.
- **Skills and tools** (a flatter, more uniform catalogue, primarily enable or disable plus a short description) fit a **flat searchable list with inline toggles**, the pattern Cursor uses for MCP servers and Claude Code uses for `/mcp`, rather than a drill-in page per tool.
- **Workflows** (a graph editor) do not fit a settings-row format in any app surveyed; the closest analogue is Windsurf's decision to pull model selection out of Settings entirely into the primary work surface. Treat the workflow list inside Settings as a launcher only, name, description, an Open button into a full-screen editor, rather than an attempt to edit the graph inline.
- **Projects** (folder, instructions, lead agent config, planning documents, a read-only memory ledger, the densest entity type described) fit **GitHub's repository-settings pattern** most closely: select a project from a list, then give that project its own full settings surface with its own sub-navigation, and keep the read-only memory ledger inline near the top of that surface, as Vercel keeps a Project ID inline rather than in a separate About tab, rather than behind an extra click.

On save model, prefer instant or autosave for toggles, selects and short fields, the majority pattern across Parts A and B, but keep an explicit Save action specifically for consequential text fields, a specialist's system prompt, a harness's default instructions, matching Vercel's and Slack's explicit-Save-for-named-fields pattern. A page-level dirty-state save bar, as already planned for Radian, is not something any surveyed app documents as its primary mechanism; VS Code's per-row modified indicator plus its `@modified` filter is the closest documented analogue and is worth studying for the visual treatment of "this field differs from its saved value," even though VS Code applies that per field with instant save rather than behind a bar.

Finally, adopt **VS Code's title-then-one-line-description-then-control anatomy** for individual fields, and **Linear's one-line description under each top-level section label**. Together these are the most concretely documented "how to keep a dense page scannable" patterns in the survey. Also adopt **Apple HIG's explicit instruction to minimise the number of settings shown at all**, and to push per-field explanation into a secondary affordance rather than always-visible text, which is useful specifically for anything in Radian's dense entity forms, agent configuration, project configuration, that would otherwise turn into a wall of labelled fields.
